# pod-sim

The only Pod process that loads CoreSimulator and SimulatorKit. Pod's runtime (`src/main/pod/sim/helper/`) starts it, talks to it over stdio and restarts it when it dies; PodNative and the runtime load no private framework. Everything private is resolved at run time (`NSClassFromString`, selectors, `dlsym`): the binary links none of it, and loads it only for a build its version table knows.

## Build

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer native/pod-sim-macos/scripts/build.sh [--single-arch | --arch arm64|x86_64]
swift test --package-path native/pod-sim-macos
```

Measurements, skipped in a plain run (`Tests/PodSimKitTests/PerformanceProbeTests.swift`): `POD_SIM_BENCH=1` times what a device's `hid` lane adds to a call; `POD_SIM_PROBE_SHOTS=1` times a screenshot's phases and `POD_SIM_PROBE_DAMAGE=1` counts SimulatorKit's damage rectangles (both on `POD_SIM_PROBE_UDID`); `POD_SIM_PROBE_UDID=<udid>` with `POD_SIM_DEVICE_SET=<set>` times `ax` per phase (frontmost, attributes, hit tests, time waiting on the device) on a booted device and the parallel read and the kept tree against the walk on that screen (node for node), `POD_SIM_PROBE_FILTER` adds a filtered run, and `POD_SIM_PROBE_TAP_LABEL` checks that a fresh connection's first tap lands. Run them in release: `swift test -c release -Xswiftc -enable-testing --filter PerformanceProbeTests`.

The script writes `.build/release/pod-sim` (universal by default) and signs it as Pod's packaging signs it: identifier `codes.pod.sim`, hardened runtime, the empty `product/entitlements/none.plist`, Developer ID from the login keychain (ad hoc when there is none; `POD_SIM_SIGN_IDENTITY` overrides).

**In Pod.app.** `product/electron-builder.pod.cjs` runs the script in its `afterPack` for the package's architecture (`--arch`; under the Xcode the release runs under, the runbook's `DEVELOPER_DIR`: `release.sh` points DEVELOPER_DIR at the Xcode whose `actool` compiles the app icon for the whole electron-builder run and passes the one it was started with as `POD_RELEASE_DEVELOPER_DIR`, which `podSimBuildEnv` puts back; started without one, xcode-select's Xcode builds it) and copies the result to `Contents/Resources/bin/pod-sim`, the one path a packaged runtime runs (`product/helper-names.cjs`, `POD_SIM`). electron-builder then signs it with the app's identity, timestamp and hardened runtime, plus `--identifier codes.pod.sim` (osx-sign would otherwise name a bare executable after its file, and viewers admit the helper by that identifier); the policy gives it no entitlements. After signing, the build fails unless `codesign --verify --strict` passes and the signature says `codes.pod.sim` and `runtime`.

## Command line

```sh
pod-sim                                   # serve protocol v1 on stdio; needs POD_SIM_TOKEN
pod-sim --selftest [--json] [--udid <udid>] [--wait-ms <n>]
pod-sim --version
```

`--selftest` exits 0 whenever it produced a report, whatever the report says; 64 is a usage error.

| Environment | Effect |
|---|---|
| `DEVELOPER_DIR` | The first Xcode to consider (an `.app` path is accepted). See "Which Xcode" below. |
| `POD_SIM_TOKEN` | This spawn's token; `hello` must carry it. Set by the runtime. |
| `POD_SIM_VERSION_TABLE` | A version-table file overlaid on the bundled one (a fix without a release). An unreadable file is reported in `table.overrideError` and ignored. |
| `POD_SIM_FORCE_UNKNOWN_BUILD=1` | Treat the build as unknown: every capability `unsupported`, screenshots through `simctl`, `hid` and `ax` refused with the reason. For the Xcode-update drill and tests. |
| `POD_SIM_DEVICE_SET` | Use this device set instead of the default. Probes only: a running Simulator.app watches the default set and opens a window for every device booted there. The pool stays in the default set. |

The runtime builds the helper's whole environment: `PATH`, `HOME`, `TMPDIR`, `DEVELOPER_DIR`, `LANG`, `LANGUAGE` and `LC_*` from its own, the token, and the three `POD_SIM_*` settings only from its explicit options (`versionTablePath`, `deviceSet`, `forceUnknownBuild`), never inherited (`src/main/pod/sim/helper/sim-helper-env.ts`). The helper's `simctl` children get its environment without any `POD_SIM_*` key, the token included. A packaged Pod runs only `Contents/Resources/bin/pod-sim`; `POD_SIM_HELPER_BINARY` and the checkout's `.build/release/pod-sim` count only when Pod is not packaged.

### Which Xcode

A Pod started from the Dock has no DEVELOPER_DIR, and the selected Xcode may be one the version table does not know while a known one sits beside it. The helper takes the first Xcode whose SimulatorKit build has a table row, looking in this order: DEVELOPER_DIR, `xcode-select -p` (run without DEVELOPER_DIR, so it prints the selection itself), then every `Xcode*.app` with bundle id `com.apple.dt.Xcode` in /Applications and ~/Applications, newest version first. It stops at the first known one, so with a known DEVELOPER_DIR nothing else is run. With none known the first one stays: unknown, so nothing private loads. It never changes the selection (no `xcode-select -s`, no sudo). The self-test reports `xcode.source` (`DEVELOPER_DIR`, `xcode-select`, `installed`), `xcode.chosenBecause`, and `xcode.candidates` (each with its SimulatorKit build, `known`, and `problem` when unusable, such as the Command Line Tools) whenever more than one was looked at; `pod-sim --selftest` prints the reason under the Xcode line.

## Protocol v1 (frozen for stages 2b and 3; with `hid` and `ax`, frozen for stages 4, 7 and 8; with the stage 2b additions, frozen for stage 8)

Runtime and helper ship in one bundle, so there is one protocol version and no compatibility window. `Fixtures/protocol-v1.json` holds the constants, the exchanges and example results; the Swift tests and the runtime client's tests both decode it.

- **Transport:** the helper's stdin and stdout. Stderr is diagnostics. At start the helper keeps a private copy of stdout for frames and points fd 1 at stderr, so a framework that prints cannot corrupt the stream. When stdin closes, the helper detaches every display and exits 0.
- **Framing:** one UTF-8 JSON object per line, `\n` terminated, at most 1,048,576 bytes before the newline, both directions. A longer request line is dropped as it arrives (never buffered) and answered with `frameTooLarge`; a reply that would be longer goes out as `{"id": n, "error": {"code": "frameTooLarge"}}` instead. Blank lines are skipped, a trailing CR is dropped.
- **Request:** `{"id": <non-negative integer>, "method": "<name>", "params": {...}}`; `params` may be absent.
- **Reply:** `{"id": n, "result": {...}}` or `{"id": n | null, "error": {"code": "<code>", "message": "..."}}`. `id` is null only when the helper could not read the request's id. Replies can arrive out of order; match by id.
- **Handshake:** the first accepted request is `hello {"token": "<POD_SIM_TOKEN>", "protocol": 1}`. Anything before it gets `helloRequired`; a wrong token gets `tokenMismatch` and the session stays locked; another protocol gets `protocolMismatch`. The token binds the session to the spawn that set the environment: with stdio no other process can reach the helper, and the token makes a helper that did not get this spawn's environment (a wrapper, the wrong binary) refuse instead of being trusted.
- **Deadlines:** each method has one, below, counted from when the request arrives. Past it the helper answers `timeout` itself and goes on serving; the work's late result is dropped. A `timeout` from `hid` means the input may have been delivered, in part or whole: read state (`ax`, a screenshot) before retrying. A `hid` call still waiting behind its device's earlier calls when its deadline passes is answered `timeout` and never sent. The runtime gives each call its deadline plus 2,000 ms in flight, counted from when the helper is ready (waiting for a helper that is starting or restarting does not count), and replaces the helper only when it stays silent that long: restart reason `timeout`. One device's slow call therefore costs that call, not every device's live view. `hello` is answered at once from the start-up self-test; the runtime allows 15 s for a spawn to reach it.
- **Events:** lines the helper sends unasked, `{"event": "<name>", "params": {...}}` with no id, only after `hello` succeeded: `inputWedged` (see `hid`) and `streamEnded` (see the live view). The runtime ignores an event it does not know, logging it.

|---|---|---|---|

The `simctl` calls inside (`io screenshot`, `list`) end after 6 s, inside these deadlines. The deadlines are in `Fixtures/protocol-v1.json` (`deadlinesMs`), which both sides' tests compare with their constants.

An attachment is held by `attachDisplay`, by each stream and by a running `settle`, and ends with its last hold; `detachDisplay` ends it at once, streams included (each reported in a `streamEnded` event, `detached`). A stream whose viewer is gone stops holding it at once. `displayStats` answers only for an attachment that still shows this boot's framebuffer: when the device shut down since, it answers `deviceNotBooted` ("...; its attachment ended") and drops the attachment, and when it rebooted since (its `lastBootedAt` moved), `notAttached`; either way later calls answer `notAttached`, never counts frozen at the shutdown.

`attachDisplay` keeps an existing attachment only while it still shows this boot's framebuffer: its surface answers and is the IOSurface a fresh lookup finds. Every lookup hands out a new descriptor proxy, so the surface, not the proxy, is the identity; after a reboot the old proxy answers no surface (both seen on CoreSimulator 1171.7). A device that rebooted gets a new attachment (`alreadyAttached: false`, counts from zero, a stderr line says why), and every attach drops the attachments of devices no longer booted, its own device's included (that attach answers `deviceNotBooted`, later stats `notAttached`). An attach runs outside the registry lock with a per-device marker: a second attach or a detach of the same device waits for it, other devices never do. A screenshot re-reads a cached main-display port only while the device is booted, and looks the port up again when the cached one has no surface.

`screenshot` reads the framebuffer when the self-test allows it and falls back to `xcrun simctl io <udid> screenshot --type=png --mask=ignored` when it does not or when the read fails (`fallbackReason` says why). The framebuffer path takes only a single-plane `BGRA` surface (CoreSimulator's, `0x42475241`); any other format goes to `simctl`, so the encoders never read channels in the wrong order. With a display attached it takes that attachment's surface without a remote call. It copies the pixels once under a read lock and keeps the copy only when the surface seed did not move during it (up to 3 tries; the device rewrites the surface in place), scales with vImage, and encodes PNG with its own encoder (16 strips filtered and deflated at level 1 in parallel, joined into one zlib stream; 8-bit RGB tagged sRGB, lossless) or JPEG with ImageIO. The file is written beside the target and renamed into place. On an iPhone 16 Pro home screen (2.5 MB PNG) a screenshot took 10.7 ms p50 and 12.5 ms p95 from the runtime's side of the pipe; ImageIO's PNG took 21 to 69 ms for the same frame. The 20 ms p95 budget stands on those quiet runs and probes (a static page 4.8 to 6.1 ms, the home screen 12.5 ms); the device e2e reports `screenshotP95Under20` as a measurement, and PERF-1's budget gate owns the binding one.

### Live view: `startStream`

The device's framebuffer goes to PodNative as the IOSurface itself, never copied: a Mach send right in a message, over a rendezvous the viewer sets up. The wire is `Sources/CPodSimSurface/include/pod_sim_frame.h` (version 1, frozen for stage 8), and `pod_sim_receive.c` there is a reference receiver the tests and probes use.

- **Rendezvous.** The viewer checks a name in with launchd (`bootstrap_check_in`), `codes.pod.native.sim.<32 hex>` or `codes.pod.native.dev.sim.<32 hex>` (the ui-host `simRendezvous` names, `src/main/pod/sim-pane/pod-sim-pane-protocol.ts`); the runtime passes it to `startStream` with the `simAttach` token and a nonce, 64 random bits it makes for the view (`simStreamNonce`, 16 hex digits on the JSON wire) and gives the viewer with the rendezvous too. The helper looks the name up once and refuses any other pattern. A name nobody checked in answers `failed`.
- **Admission.** The viewer accepts a message only from a sender that meets `anchor apple generic and certificate leaf[subject.OU] = "75Y2KR6P5W" and identifier "codes.pod.sim"`, checked from the message's audit token (`SecCodeCopyGuestWithAttributes`, then `SecCodeCheckValidity`), once per sender process (pid and pidversion), and then keeps it only when it carries the nonce the viewer was given: a process that meets the requirement and learned the name (another Pod's helper, an old stream under a reused token) still cannot feed it frames. Admitting one process (pid and pidversion) instead of the requirement is for tests only. Every message the viewer does not keep is destroyed with its rights (`mach_msg_destroy`), and the surface is taken only as a send right.
- **Messages.** A surface message (id `0x504f5331`, 96 bytes) carries the surface's Mach right, its id, size, scale x100 and seed; it goes first, again after the device swaps surfaces (a reboot, a mount), and again after a full queue held it back. A frame message (id `0x504f5332`, 88 bytes) goes once per presented frame whose seed changed, carrying the frame number, surface id, seed and a damage rectangle; nothing goes while the screen is static. Damage is the whole surface: `POD_SIM_FRAME_DAMAGE_EXACT` is reserved and never set at version 1, because SimulatorKit's damage callback, the one idb reads, delivered 181 calls and no rectangle in 3 s on CoreSimulator 1171.7. Every message carries the token and the nonce (a 64-bit field after the 32-bit `reserved` one, which stays zero; every older field keeps its offset), so a viewer drops a stale stream's messages.
- **Tearing.** The device writes the same surface in place. A viewer copies or samples it and keeps the result only when `IOSurfaceGetSeed` equals the message's seed before and after; a mismatch means a newer frame message follows. On a device animating at 60 fps, 1,113 of 1,145 frames read clean, 6 were already superseded on arrival, 26 moved during the read, and none tore unseen.
- **Never waits, keeps nothing.** Sends use a zero timeout. A viewer whose queue is full loses that frame (`framesDropped`), and the newest frame is sent again after 8 ms, doubling to 512 ms; one retry is in flight per stream. A message that timed out comes back with its rights (the kernel pseudo-receives it) and is destroyed, so a stuck viewer costs no reference per dropped frame and no framebuffer stays alive in a dropped surface message. A viewer that is gone (`MACH_SEND_INVALID_DEST`) ends its stream at once: it leaves `displayStats`, the runtime gets `streamEnded` (`viewerGone`), and when nothing else holds the display (no other stream, `attachDisplay` or `settle`) it detaches, because an animating device costs a frame callback per frame with nobody watching.
- **`streamEnded`.** `{"event": "streamEnded", "params": {udid, token, nonce, reason}}` for a stream that ended without `stopStream`: `viewerGone` (forget the view), `deviceShutDown` (the device is not booted; start the view again after a boot), `deviceRebooted` (its display was replaced; call `startStream` again), `detached` (`detachDisplay` ended it, as a pool reset does; call `startStream` again to keep showing the device). The helper sees a shutdown or reboot when a call next touches the device's display (an attach of any device drops those no longer booted, and `displayStats` or a screenshot of the device checks its boot), not by itself. A device that rebooted keeps its streams when an attach replaces its display first (they move to the new boot, a surface message first). After a reboot the runtime calls `startStream` again for every view it still shows, with the same service, token and nonce; the helper replaces a stream with the same token. The `nonce` names the generation, so an event for a stream that was started again under its token is ignored. ui-host maps these to `simDetached` (stage 8): `deviceShutDown` to `deviceLost`, `detached` to `detached`, and the runtime's own `helperRestart` below to `helperExited`.
- **Cost.** With one stream on a device animating at 60 fps the viewer received 60.3 fps, the helper used 0.75% of a core (125 µs of CPU per frame, the frame callback itself 5.3 µs p50 and 8.6 µs p95, `callbackMicros`), and transit to the viewer was 26 µs p50. A static screen cost 0.0 CPU seconds over 60 s.
- **After a helper restart.** The runtime starts every stream again on the new helper under the same token and nonce (the viewer's name is still checked in); `seq` starts again at 1 with a surface message first. For a view the new helper refuses, and only for one, the runtime reports `streamEnded` with reason `helperRestart` itself (the helper never sends it), and ui-host publishes `simDetached{reason: 'helperExited'}`.

### `settle`

Waits until the screen stops changing, for a person or an agent about to read it. Settled means: for a whole `windowMs` nothing moved but small regions, and two accessibility reads made inside that still window agree (`fingerprint`, which leaves out carets, spinners and focus). A moving region is small when it is at most `smallPt` points on each side, and at most 4 of them are allowed (a caret, a spinner, a blinking dot); more small regions than that is a moving screen (a list of shimmering cells), and then all of them count. A screen that never settles is not an error: at `timeoutMs` the answer is `settledWithMotion`, with `motion` naming the regions still moving, largest first, in points of the device's native (portrait) orientation; `ignored` lists the small ones settle allowed.

What moved comes from the framebuffer: on each frame (at most every 33 ms, and once more after the last) the helper hashes the surface in 16-pixel tiles (`pod_sim_tile_hashes`, read-locked, about 0.8 ms for an iPhone 16 Pro frame in release) and joins changed tiles into regions (8-connected bounding boxes). A screen already attached and without a frame for a window settles on its reads alone. Without a live display (no `display` for this build), or when the framebuffer cannot be hashed (no surface yet, or not 4 bytes per pixel), two reads a window apart decide (`basis: "tree"`); without a translator for this build, or when a read fails, pixels alone decide (`basis: "pixels"`); with neither, settle is `unsupported` (`failed` when the framebuffer cannot be hashed and there is no translator), and one whose tree reads fail with no pixels to watch answers `settledWithMotion`: settle never calls a screen it cannot see settled. On a device: a static page settled in 135 ms, a blinking caret in 523 ms (ignored 6 by 38 points), a spinner in 448 ms (ignored 38 by 33), and a shimmering list answered `settledWithMotion` at its 3 s timeout with its 6 bars.

### `hid`: touch, keys, buttons

Coordinates are device points with the origin top left, the space `ax` frames are in; a point off the screen is `badParams`, never clamped. Every event goes to the device's `dtuhidd` (`com.apple.coredevice.feature.remote.hid.digitizer`) over one XPC connection per device, made the way idb v1.7.2 makes it and kept until it breaks; a connection whose liveness barrier does not come back within 4 s is refused (the daemon may still be starting) and the next call connects again. A fresh connection waits 200 ms after that first reply before its first event, as idb does (`replyTail`), so a cold first tap is not dropped. After the last event the helper sends a barrier and answers only once `dtuhidd` has handled everything; a barrier that does not come back in 2 s fails the call and drops the connection.

**Order and backpressure.** A device's `hid` calls run one at a time, whole (connecting, the pasteboard, the events, the barrier), in the order the requests arrived on stdin; devices never wait on each other. A device holding 16 calls (the running one and those waiting) answers the next one `busy` at once, and nothing of it is sent: at pointer rate (stage 8 streams `touch` at 60 to 120 a second, each answered in a few ms) 16 is about 130 ms of input, and a device that falls that far behind should get fewer moves, not stale ones later. A caller that gets `busy` for a `touch` `up` must send it again, or the finger stays down.

**A stuck call.** A thread in a private call cannot be stopped. When a device's running `hid` call is still running 2 s past its deadline (it was answered `timeout` then), the next call for that device gives the lane up: the calls waiting behind the stuck one are answered `wedged` and never sent, the device's input connection is dropped (a connect still under way is discarded when it returns), and the new call runs on a fresh lane. Other devices never notice. The helper then sends `{"event": "inputWedged", "params": {udid, stuckMs, dropped, abandoned, recycleAdvised}}`; each abandoned lane keeps a stuck thread, so from the second one on `recycleAdvised` is true and the runtime replaces the helper with its restart backoff, starting every live view again on the new one.

**Orientation.** `dtuhidd` takes points in the screen's native, portrait space, and in landscape the tree's points are the interface's, rotated. Which landscape (left or right) the tree cannot tell, and no mapping has been verified on a device, so `hid` maps portrait only: while the device's latest `ax` snapshot found the app in landscape (`screen.orientation`), an action that starts a contact (`tap`, `longPress`, `swipe`, `drag`, `pinch`, `touch` `down`) answers `unsupported` with the reason; a `touch` already down may still move and lift, and `text`, `key` and `button` carry no points. A new snapshot in portrait lifts it; a device with no snapshot since boot is sent as portrait. Stage 8 owns the landscape mapping: its pointer works on the framebuffer, which stays in the native space.

| `action.kind` | Fields (defaults) | What the device gets |
|---|---|---|
| `tap` | `x`, `y`, `holdMs?` (60; 1 to 5000) | one contact down, held, up |
| `longPress` | `x`, `y`, `durationMs?` (1000; 300 to 5000) | the same, held longer |
| `swipe` | `from`, `to`, `durationMs?` (300; 50 to 5000), `edge?` (`left`, `right`, `top`, `bottom`) | a contact moving every 16 ms, held at the end before it lifts; `edge` marks it as starting on that screen edge (iOS's back and home gestures) |
| `drag` | `from`, `to`, `pressMs?` (600; 0 to 3000), `durationMs?` (500), `releaseMs?` (200; 0 to 2000) | press and hold, move, hold, lift: what a drag-and-drop needs |
| `pinch` | `centre`, `fromSpan`, `toSpan` (1 to 4000 points between the fingers), `durationMs?` (400), `angle?` (degrees, 0 side by side) | two contacts moving apart or together |
| `touch` | `phase` (`down`, `move`, `up`), `points` (1 or 2), `edge?` | one raw phase, for a person's pointer (stage 8) |
| `text` | `text`, `via?` (`auto`, `keys`, `paste`) | see below |
| `key` | `key` (a name from the contract's `SIM_KEYS`, or one printable ASCII character) or `usage` (HID keyboard page), `modifiers?` (`shift`, `control`, `option`, `command`), `phase?` (`press`, `down`, `up`) | the key with its modifiers held around it; a character that needs shift on a US layout gets it |
| `button` | `button` (`home`, `lock`, `siri`, `volumeUp`, `volumeDown`), `holdMs?` (100) | the hardware button |

No action may plan more than 8 s of events: with connecting (4.2 s at most) and the barrier (2 s) it ends inside the 15 s deadline (`InputRun.worstCaseSeconds`, checked by a test). `waitForFrameMs` reports `frameAfterMs`, the time from the first event to the first frame the device draws after it, waiting at most that long after the first event (absent when none comes in time): the input-to-damage latency stage 0 measured.

**Text.** `auto` types printable ASCII (plus newline and tab) of at most 250 characters as US-layout key presses, 12 ms apart. Anything else goes through the device's pasteboard (`xcrun simctl pbcopy`, run with `LC_ALL=en_US.UTF-8` because it decodes stdin in the locale's encoding and a Pod started from Finder has no locale: "zażółć" landed as MacRoman mojibake without it; given 2.5 s, after which the call fails with nothing sent) and Cmd+V, up to 4,096 characters; a paste refuses `waitForFrameMs`, since its answer waits on the app (the worst case is 13 s); `keys` refuses text with a character that has no US key and names it. A paste into an app that has not been granted the pasteboard makes iOS ask "Allow Paste": the helper watches for 600 ms whether SpringBoard takes the screen and then answers `alert: "pastePermission"`; the prompt's buttons are in `ax`, and the text lands once "Allow Paste" is tapped. `xcrun simctl privacy <udid> grant pasteboard <bundle id>` (not in `simctl`'s list, but passed through to `kTCCServicePasteboard`; seen on iOS 26.5) grants it ahead, after which a paste needs no tap. Both paths typed "zażółć gęślą jaźń" exactly (2026-10-16).

### `ax`: the accessibility snapshot

The frontmost application's tree (SpringBoard on the home screen and while a system prompt is up), at most 2,000 elements and 80 levels, within a 2.5 s read budget, in the shape macOS's AccessibilityPlatformTranslation gives it. With `parallelWalk` (the bundled table's pick for translator 587) the helper builds the translator's own requests and sends them straight to the device's `com.apple.CoreSimulator.accessibility` service (`transport: "bridge"`) over up to 8 connections at once: one for the frontmost application, then one batched attribute request per element (the one `accessibilityMultipleAttributes:` sends, as idb v1.7.2 reads), each element's children asked for as soon as its answer lists them. The service answers different connections at once and one connection's requests in order, so a read costs about the tree's depth in round trips instead of its size, and each connection carries one request at a time. The answers are converted by the translator's own element methods, so the nodes are the ones the translator walk gives; checked node for node on the Settings list, the home screen and Safari with the keyboard up. Past 2,000 elements the parallel read keeps the shallower ones, where the walk kept the first 2,000 in its order.

When a parallel read fails (no service, no answer to the first request, a value the read cannot convert without asking the device again), the same call reads through the translator the way stage 3 did, one request at a time (`basis: "translator"`, with `fallbackReason`): straight to the service, or through `-[SimDevice sendAccessibilityRequestAsync:...]` when that service cannot be reached (`coreSimulator`). A parallel read past its 2.5 s budget is answered as it failed: the translator would share that budget and has none left. Two such failures in a row for one boot of a device (a read past its budget does not count) pause parallel reads of it for 30 s, so a broken route costs one try per pause instead of up to 1.5 s on every call; a failure after a pause starts another, a success or a new boot starts over, and the self-test always tries it. stderr names each reason once per device boot. The translator is single-threaded, so walks of different devices take turns; a device whose accessibility server hangs costs others at most the budget. A table that picks `translatorWalk` always reads that way.

**The kept tree.** Each device's last parallel read is kept with a stamp taken before it was read: the count of accessibility notifications the device sent and `hid` calls this helper carried (counted when a call arrives and again when it ends), and the main framebuffer's IOSurface id and seed, which moves whenever the device draws. An `ax` whose stamp is unchanged answers from the kept tree (`basis: "cache"`, reusing the hit tests already made and making only missing ones); any notification, input or redraw since, a reboot included, reads again (`basis: "parallel"`). A tree read while the screen changed is never answered from, since its stamp predates the change. A change with neither a notification nor a redraw (a node off the screen, a label only accessibility sees) is answered from the kept tree until something draws or notifies; `fresh: true` always reads. `all: true` does not read fresh by default: what it adds is off-screen and covered nodes, which nothing taps (a tap lands only on a visible node, whose changes draw), and the runtime's tap by label asks with `all: true` to name an off-screen match in its refusal, so a fresh read there would put a whole read and its hit tests (p95 about 30 ms at a calm moment, see Speed) in front of every tap; a caller that needs off-screen truth, such as a full listing for a person, passes `fresh: true`. `settle` and the self-test read fresh; settle keeps its reads, so once it says the screen is still the next `ax` answers from its last read. Notifications come over one connection per device opened only to hear them (the service sends them to every connection that has asked something, so a read's connections close with the read); without it, or without a readable framebuffer (`screenshot` not `ok`), nothing is kept, a read without a stamp leaves the kept tree as it was, stderr says why once per session, and the self-test's `ax` note ends with "no tree is kept: " and the reason. Nothing polls: the counter moves only when a notification or an input arrives, and a device's session (the service endpoint, that connection and the kept tree) closes 120 s after its last `ax` (stderr says so); the next one looks the service up again (a CoreSimulator call, about 1 ms) and opens a new connection.

**Speed.** iPhone 16 Pro, iOS 26.5, macOS 27.0.1, release build, load average 31 to 48, the helper's own time over 30 calls each (`PerformanceProbeTests`, `ax routes`): the Settings list (14 elements) read fresh in p50 19 ms, p95 32 ms, and from the kept tree in 0.5 ms and 1.5 ms; the home screen (13) in 16 ms and 19 ms, kept 0.6 ms and 2.2 ms; Safari with the keyboard up (42) in 28 ms and 31 ms, kept 0.7 ms p50 (11 of the 30 calls read again, since the caret redraws). The translator walk took p95 61, 61 and 90 ms on the same screens. On a device seconds after boot the first read can find the service not answering yet and go through the translator; the next one is parallel.

`screen` is the application element's size in points, so it follows the app's orientation; `orientation` is `portrait` when that size is the native screen's (or its full height, an iPad split view), `landscape` when it is the native screen turned, and absent when it is neither (a Slide Over or Stage Manager window).

Nodes are the contract's `SimNode`, field for field: `index` (walk order, stable across `filter`), `role`, `label` (the element's description), `value`, `id` (accessibility identifier, the test id), `centre`, `frame`, `visible`, `enabled?`, `selected?`, `focused?`; texts are cut to 120 characters with "…". The application element itself is not a node. `centre` is the middle of the part of the frame that is on screen: a tap there lands on the element even when it is cut by the screen edge. `visible` is false for a hidden element, one without area (a frame the translator reports as NaN or infinite becomes zero-size at the origin, rather than failing the snapshot), one off screen, and, with `hitTest`, one whose centre answers with another element of the same app (covered by a sheet or the keyboard); a hit on its own descendant or ancestor counts as itself, and content another process draws inside the app (web content, widgets) cannot be told apart, so it stays visible. Each hit test is a round trip to the device, so only nodes that could be listed (on screen, not hidden, matching `filter`) are tested, and only where another element of the walk, outside the node's own ancestors and descendants, spans the node's centre: a cover the walk never saw is not detected. In Settings on iOS 26.5 that took an unfiltered snapshot from 14 hit tests to 3, and a filtered one to 0 or 1. Without `all`, only visible nodes are listed and the rest are counted in `notVisible`. `filter` matches label, value or id, ignoring case and diacritics (ł has no decomposition: "lodz" does not find "Łódź"). `total` counts what is eligible, `shown` what is listed (at most `maxNodes`), `omitted` the rest: the contract's "+N more".

`alertSuspected` is true when the tree collapsed to the application element: system UI no tree shows (the keyboard's first-use tip, AutoFill's "Save Password?") may cover the app, and a screenshot is the only way to see it. An app that is still launching collapses the same way for a moment. Web content in Safari and in web views is not in the tree.

`fingerprint` (16 hex characters) changes only when what is on screen changes: it covers role, label, id, value, the frame rounded to whole points, hidden, enabled and selected, and leaves out focus and the values of progress and busy indicators and of elements that say they update frequently (a caret, a spinner). Stage 2b's settle compares two.

### Public fallback seam

When the table gives `hid` or `ax` no private implementation (an unknown build, a row without them, an unlisted translator build for `ax`), the call goes to a public fallback by UDID before any device lookup, since CoreSimulator is then not loaded. None ships: the call answers `unsupported` with the table's reason and "no public input fallback in this helper (an XCTest driver is owed)". A fallback that acts answers in place of the private path, and the seam sets `degraded` to the table's reason (`ax` also reports `transport: "fallback"`).

Error codes: `badFrame`, `frameTooLarge`, `helloRequired`, `tokenMismatch`, `protocolMismatch`, `unknownMethod`, `badParams`, `unsupported` (the table has no implementation for this build), `failed` (it has one and it failed here), `deviceNotFound`, `deviceNotBooted`, `notAttached`, `writeFailed`, `simctlFailed`, `timeout` (for `hid`: may have been delivered), `busy` (the device's `hid` lane is full; nothing was sent), `wedged` (the call waited behind one stuck in a private call and the lane was given up; nothing was sent), `internal`.

### The self-test report

`{protocol, helper: {version, pid}, xcode?: {developerDir, source, version?, build?, chosenBecause?, candidates?}, coreSimulator?, simulatorKit?, macOS?: {version, build}, accessibilityTranslation?, problem?, table: {known, entry?, source, override?, overrideError?, forcedUnknown}, capabilities: {display, screenshot, hid, ax}, deviceSet?, device?, fallbacks?}`. Each capability is `{status: ok | unsupported | failed, implementation?, checked: table | symbols | surfaceOnly | device, reason?, note?, framesSeen?}`. The order of the rules is the contract (`SelftestVerdicts`): no usable Xcode makes everything `unsupported`; then the table decides; a picked implementation whose frameworks do not load, or whose probe fails, is `failed`; a probe that passes is `ok` at the level it reached. On a device, `hid` connects to `dtuhidd` and waits for a barrier; `ax` reads the frontmost application's root, and its note says whether that read went in parallel or through the translator, and why.

`display` on a device waits up to `waitMs` for a frame callback and reports `framesSeen`. It is `ok` at `device` only when frames arrived; a surface with no frame (the screen did not change while it waited) is `ok` at `surfaceOnly`, which is no proof of a live view: stages 2b and 4 treat only `device` as one. No callback at all, or frames without a surface, is `failed`.

## Runtime client

`SimHelperSupervisor` (`src/main/pod/sim/helper/`) keeps one helper for every device and answers every call with a typed result; nothing it does throws, from a call or from its restart timer. A spawn that fails (thrown or reported) is `spawnFailed`; an exit is `crashed`; a helper silent past a deadline plus the margin is killed with reason `timeout`. Each of these restarts after 250 ms doubling to 30 s, back to 250 ms once a helper lived 60 s. `tokenMismatch` and `protocolMismatch` are permanent for that build: no restart timer, and later calls (and `start()`) answer the same failure without spawning until the binary at the resolved path changes (its device, inode, size or mtime, read on each call), which is how a rebuild or an app update is noticed.

Events reach `onEvent` after the supervisor acted on them. `inputWedged` is logged; with `recycleAdvised` the helper is killed with reason `wedged` and restarts with the same backoff. `streamEnded` forgets that view (only while its nonce is the one remembered). The supervisor remembers every `startStream` that succeeded and has not been stopped, each one a generation of its view, and replays them on each new helper as soon as it is ready. A replay the helper refuses (the viewer is gone, the device shut down) is forgotten and reaches `onEvent` as `streamEnded` with reason `helperRestart`. When the caller stops or starts a view again while its replay is under way, the replay stops only its own stream (`stopStream` with its nonce), and when that stream had replaced the caller's newer one in the helper, it starts the caller's again.

## Version table

Data, keyed by the exact `CFBundleVersion` of CoreSimulator and SimulatorKit (Xcode 26.6 and 27.0 both ship SimulatorKit "16.0", as 955.7 and 1005.2). Versions are read from the frameworks' Info.plists before anything loads, so an unknown build never runs private code. The bundled table is `Sources/PodSimKit/VersionTable/BundledVersionTable.swift`; an override file has the same shape and its rows replace bundled rows for the same build pair:

```json
{"schema": 1, "builds": [{"name": "Xcode 27.0 (27A266a)", "coreSimulator": "1171.7", "simulatorKit": "1005.2",
  "capabilities": {"display": "screenCallbacks", "screenshot": "surface"}, "verified": "..."}]}
```

A capability left out of a row is unsupported for that build (that is how a row blocks one). A name this binary does not implement is unsupported, never attempted.

`ax` has a second key. AccessibilityPlatformTranslation ships with macOS, not with Xcode, so a row's `ax` counts only where the translator's own build (its `CFBundleVersion`, reported as `accessibilityTranslation.build`) is listed under `accessibility` with the same implementation; otherwise `ax` is `unsupported` ("AccessibilityPlatformTranslation <build> is not in the version table for ax", or "... is listed for ax <other>, not <name>") while the rest of the row stands. One pair agrees though named differently: `parallelWalk` falls back to `translatorWalk`, so a row naming one and a translator entry naming the other (an override written before stage 3b) read through the translator. Keyed by the framework rather than the macOS build, a macOS point update that leaves the translator alone leaves `ax` on; `macOS` in an entry is information only. An override's `accessibility` entries replace bundled ones for the same translator build, and an override without `accessibility` leaves the bundled ones in charge:

```json
{"schema": 1, "builds": [],
 "accessibility": [{"name": "AccessibilityPlatformTranslation 1.0 (587)", "translator": "587", "ax": "parallelWalk", "macOS": "27.0.1 (26A434)", "verified": "..."}]}
```
